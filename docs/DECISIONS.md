# Engineering decisions

## Scope and assumptions

The explicit TECH STACK and monorepo layout take precedence over the contradictory Laravel, FormRequest, Artisan, Composer and PHPUnit references. All equivalents use Node 20+, Fastify, Zod, Knex and Vitest. No PHP installation is needed. This is a local application, not a hosted Sites deployment. Optional queues, rollups and bot filtering beyond a simple UA rule are intentionally out of scope.

## Storage and identity

Browser and server use the same UUID-v4 event envelope. `timestamp` becomes `occurred_at`; `received_at` is assigned at ingestion. Both are canonical 24-character UTC ISO strings so comparisons work identically across SQLite, Postgres and MySQL. Dashboards use occurred-at. Ingestion rejects dates older than 7 days or more than 24 hours ahead. The historical demo generator writes trusted fixtures directly so it can populate two weeks without weakening that rule.

Unique visitors count `COALESCE(user_id, anonymous_id)` within the range. Identity is attached only to subsequent events, with no retroactive merge, so a person who identifies can count twice. Sessions count distinct session IDs. The SDK persists anonymous identity and a session with a 30-minute inactivity timeout; reset starts both identities anew. A browser forwards anonymous/session/user IDs to checkout, linking its order event. Fake identification hashes an entered email in the browser and never sends the email or name to analytics. A hash is still a pseudonymous identifier, not anonymization.

Properties are JSON objects, at most 8 KiB in UTF-8, with depth <= 6; context is bounded too. The SDK collects page context but strips URL query strings and fragments by default. Applications must avoid personal data in event properties, paths and titles. No IP addresses are stored. User-agent text is untrusted, bounded to 500 characters, and never used for identity. `BLOCK_BOTS=true` optionally rejects known bot-like agents; it is not a security boundary.

Indexes: the unique project/event pair prevents retry duplicates. Project/time supports every range query; name/time supports event filtering; path/time supports page breakdowns; anonymous/time supports visitor investigations. Tenant project scope is always included. At scale add daily rollups, dialect-specific DB timezone grouping, partitioning and eventually a column store such as ClickHouse. Indexes increase write cost; retain only those justified by query plans.

## Credentials and deployment

Local demo keys are documented in `.env.example` and loaded through `.env` or process environment; missing API credentials fail startup. Vitest injects the example environment for isolated tests. Public keys identify projects, not secrets. Public ingestion requires an exact allowed Origin and browser source; server source requires a SHA-256 hashed, high-entropy secret bearer key. Beacon sends the public key in the JSON body because it cannot set headers. Preflight is allowed only for a project-approved origin, while the actual request also validates its key. Query endpoints use one static dashboard bearer token scoped to the seeded demo project. The Next server proxies queries so the token is never bundled in browser code. Replace this with per-user authentication, project authorization, HTTPS and credential rotation for production.

Rate limiting is an in-memory fixed window per valid credential, 120 requests/minute by default, with Retry-After. Multi-instance deployments need a shared limiter. Browser localStorage and cookies require a real consent policy in production; Do Not Track and opt-out are honored. Cross-device identity merging, consent UI, sampling and event schema versions are future work.

## Portability references

Knex's [conflict handling](https://knexjs.org/guide/query-builder#onconflict) emits conflict-ignore SQL for supported engines. Fastify's [body limit](https://fastify.dev/docs/latest/Reference/Server/#bodylimit) enforces the 256 KiB ingestion bound before parsing. SQLite is exercised locally; Postgres/MySQL drivers are included, with portable migrations and queries, but need integration runs against real services before a production switch.

## Ingestion and delivery

Audit clarification: the newer QA request explicitly requires clean 4xx responses for wholly invalid oversized/deep properties. Entirely rejected batches therefore return 422 with indexed reasons; partially valid and duplicate-only batches remain 202. This supersedes the earlier all-invalid-202 choice. Browser requests abort after ten seconds, then use normal retry/backoff. Opt-out cancels pending delivery/backoff; a newer cookie consent value takes precedence over stale readable localStorage when writes fail. Shutdown sends a best-effort beacon, aborts fetch and clears its timers/listeners; persisted unacknowledged events remain replayable.

Ingestion is synchronous by default: validate each event, lock the project row on Postgres/MySQL, look up existing UUIDs, then perform one bulk conflict-ignore insert inside a transaction. SQLite's single-connection pool serializes writes. UUIDs are deduplicated within batches and against storage, and counts report accepted/duplicate/rejected separately. The lock gives exact duplicate accounting with concurrent writers but serializes writes per project. Replace it with dialect-specific affected-row accounting under higher throughput. No heavy aggregation or network work occurs in ingestion. The optional asynchronous ingestion flag is not implemented; accepted means persisted, not just queued.

SDK batches up to 20 events every 5 seconds by default, capped at 50, with a 200-event persisted queue. Batches also stop below 60 KB for the browser's keepalive/beacon payload ceiling, and acknowledged flushes drain sequentially. New events evict the oldest when full. Identity uses localStorage with cookie fallback, then memory when both are blocked. Queue persistence uses localStorage only. Storage keys are scoped by public project key. Multiple tabs can race on the persisted queue/identity; this small SDK has no cross-tab coordinator. Consent preference persists. DNT remains authoritative even after optIn.

Fetch uses keepalive; network errors, 5xx and 429 retry with exponential jitter, respecting Retry-After, capped at five attempts per queued event. Other 4xx responses are dropped; 202 acknowledges the submitted batch even if some events were individually rejected. Beacon uses a JSON Blob and body write_key. Beacon has no acknowledgment, so events remain persisted for a later fetch and may replay. UUID uniqueness prevents double counts. If the browser never returns or exhausts retries, events may be lost. This is best-effort analytics, not a financial ledger. Debug logging is opt-in.

History patches are shared/ref-counted across SDK instances and restored on shutdown when still owned. Auto page views dedupe identical full URLs; query/fragment changes can create another page view but those components are omitted from context. Manual page() intentionally records even on an unchanged URL. React provider options should have stable identity. Route events record current document title; framework title updates may finish later.

## Queries and timezones

All filtering is project-scoped and uses occurred_at with parameter binding. Overview, pages, event breakdown and series are grouped SQL queries. SQL aggregation counts visitors within each bucket; it does not add distinct counts across smaller sub-buckets. Timezone conversion is isolated in `buckets.ts`: Intl discovers offset segments (including DST), and a small dialect helper shifts UTC before formatting. MySQL does not need loaded named-zone tables. Offset changes are found with six-hour probes and binary search. This targets modern IANA zones; two changes within six hours in historical timezone data are outside this demo's assumptions. Missing buckets are generated independently then zero-filled. Local repeated fall-back hours combine; spring-forward missing hours are absent. UTC inclusive range bounds do not shift with tz. Max query span is 90 days, bounded recent/top-page limits are 100, and no event rows are loaded to compute aggregates.

## Business flow and known limits

Orders store integer cents, compute totals from menu data, reject duplicate line IDs, and write order + items atomically. No payment, inventory, tax, shipping, authentication or production checkout idempotency is implemented. Receipt URLs use UUIDs but still need ownership authorization in a real product. The menu snapshot in the cart is only a display estimate; the server is authoritative.

The Node tracker supports in-process and bearer-authenticated HTTP transports without Fastify or Knex dependencies. The demo schedules work after the checkout response, after a successful transaction. Shutdown drains outstanding tracking promises. This avoids response latency, but a crash between commit and tracking can lose an event. For production use a transactional outbox written with the order, then a durable queue worker with retries and stable UUIDs. Never just fire a business event before commit. The external HTTP transport retries three times with stable envelopes and a five-second request timeout; callers decide where to schedule it.

The synthetic traffic generator inserts 14 days directly using deterministic UUIDs; it is not an ingestion authentication bypass exposed over HTTP. It models repeat visitors, sessions, identification and funnel drop-off, with historical order events but no synthetic business order rows. Repeating a date's fixtures preserves earlier data. Removing old fixture dates/retention is an operator responsibility.

The local Next dashboard proxy intentionally exposes aggregate/recent data to visitors of the local app, while keeping the static API token out of browser bundles. Real auth, authorization, TLS, key rotation, shared throttling, retention/deletion/export, consent and abuse protection are prerequisites for public hosting. The dev origin has a documented default, and demo secrets live only in the example environment and docs; no production credential is embedded. Optional Google Fonts affect typography only; system fallbacks work offline. Automated backend/SDK and production build checks run locally; browser QA verified the dashboard and full checkout through the live event feed after the preview attached. The React provider reuses its tracker across Strict Mode effect replay so development mounts do not double-count initial page views. No Postgres/MySQL services were available for runtime checks.
